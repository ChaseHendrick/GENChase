# Full rerun of the note's programs from the downloaded inputs (2026-09-27)

The rerun that quality item 7 asks for: every program in `code/` run again from the downloaded inputs, from a copy
of this folder, each output compared with the committed one, then `code/make_numbers.py`, `code/make_figures.py` and
the LaTeX build run on the rerun `out/`.

**Result.** Every program ran to completion and every value reproduces. At the README's setting (one BLAS thread)
every output is byte for byte or array for array the committed one, apart from two things. First, the outputs of
`matern_window.py` (spectra, window exponents, geometry) were committed from a two-thread run and differ from a
one-thread run in the last bits; their rows are also written in a different order. Second, the finite-population file
`out/matern_finiteN.json` could not be regenerated by the README at 67df917. It holds 112 cells, 54 with 20 replicates
and 58 with 5, as the Methods describe, but `matern_finiteN.py` listed only 108 of them, and the README's single
command gave every cell 20 replicates. That was fixed in 4d6c418 (section "The finite-population file"): the program
lists all 112 cells, and the README runs it in two stages. The fixed program, run from the README's commands,
reproduces the stored cells it was given to compute, and the documented procedure reproduces the whole stored file,
every one of its 1,370 replicate values included. `make_numbers.py` reproduces `paper/numbers.tex`, the five tables,
`out/tab_grating.tex` and `out/numbers.json` byte for byte from the committed `out/` and from the rerun `out/`, and
the figures and the PDF text are identical. Item 7 is checked on this evidence.

**Why the two-thread runs were redone.** The MEME fits are ill-conditioned in the last bits (the full whitening
matrix has condition number 7.7e7). With the two-thread kv parts and data sets (differences of 1e-13 and 4e-16),
`meme_analyze.py` moved alpha2 by up to 5.2e-5; with the two-thread kvN parts as well, by up to 8.7e-4 and a misfit
by 0.11 (in both runs no flag or break changed). `precision_check.py` moved its full-whitening alpha2 by up to 5.5e-7,
which changed the printed `\PrecAlphaMax` from 1.2e-7 to 2.9e-7; its first, all two-thread run also moved
`\PrecCvMax` from 3.1e-7 to 1.1e-7 (single-precision cvPCA). Two diagnostics isolate the cause. Run with one thread
on the committed inputs, `meme_analyze.py` reproduces the committed `meme.json` byte for byte (593 s), and
`precision_check.py` reproduces the committed `precision.json` (439 s). The one-thread chain (calibration,
`meme_sim.py`, kv, `meme_analyze.py`, `precision_check.py`) then reproduces both files byte for byte, and
`\PrecAlphaMax` with them.

## The first run of `verify_independent.py` (exit code 1)

This was a problem in the scheduling harness, not a disagreement in the results. The scheduling script started
`verify_independent.py` once `matern_window.py` had stopped. But `matern_window.py` had been stopped by its time
limit (exit 124) before it wrote `out/matern_window.json`, so `verify_independent.py` failed at once with
`FileNotFoundError` on that file. Started again after `matern_window.py` finished with exit 0, it passed every check.
Only the scratch scheduling script was at fault.

## The finite-population file

**What differed at 67df917.** Two things kept the README from regenerating `out/matern_finiteN.json`:

1. **Cell list.** The Methods (and the program's header) describe nu = 1 at every ell >= 1/4 and nu = 0.75 at
   ell = 2, 4, 8 on all ten sets, plus all five nu at ell = 1/4, 1, 4 on 8D MP032 2017-08-10 and 4D MP032 2017-09-22.
   That is 112 cells, the number the committed file holds. The program's `keys_for` added only nu = 0.5, 1.5 and
   2.5 on those two sets, so it computed 108. The four missing cells were nu = 0.75 at ell = 1/4 and 1 on the two
   sets, with 20 replicates each in the stored file.
2. **Replicate counts.** The stored file has 20 replicates in the 54 cells of the first computation and 5 in the 58
   added in revision, as the note says (`\FinRFirst`, `\FinRAdded`). From an empty `out/`, the README command
   `matern_finiteN.py 20` gave every cell 20 replicates, and no README command gave the added cells 5.

With that command, `make_numbers.py` on the rerun `out/` changed ten macros (committed, then rerun): `\FinCells` 112 to
108, `\FinRAdded` 5 to 20, `\FinSDMax` 0.0021 to 0.0014, `\FinBorderShiftMax` -0.002 to -0.003,
`\FinReachMarginEight` 0.0035 to 0.0032, `\FinReachMarginFour` 0.0926 to 0.0924, `\FinReachMarginSDEight` 0.0021 to
0.0014, `\FinReachMarginSDFour` 0.0021 to 0.0013, and `\FinReachMarginREight` and `\FinReachMarginRFour` 5 to 20. It
changed five lines of the PDF text. The tables and figures were unchanged.

**The fix (4d6c418).** `keys_for` lists the four cells (nu = 0.75 joins the nu added on the two sets, except at
ell = 4, where the cell is already in the base list). `first_run(key)` names the first computation's cells: ell = 1/4,
1 or 4, with nu = 1 on every set and every nu on the two sets. A `--first` option restricts a run to them. The README
runs the two stages:

```
python3 code/matern_finiteN.py 20 --first    # the 54 cells of the first computation, 20 replicates
python3 code/matern_finiteN.py 5             # the other 58 cells, 5 replicates
```

The Methods sentence on replicate counts now names the first computation's cells. No number in the note changed; the
rebuilt PDF has 16 pages, and its text differs from the previous PDF only in that sentence.

**Why the stages set only the replicate counts, by construction.** In `matern_finiteN.py` replicate r's Wishart
matrix is `bartlett(np.random.default_rng([20260926, 7, r]), P, NN)`. It is a fresh generator per replicate, seeded
by r alone, and it consumes a fixed number of draws (P(P-1)/2 normals, then P chi-squares). Each cell's value for
replicate r is the window exponent of `eigvalsh(D^1/2 W_r D^1/2)`, which depends only on W_r and that cell's spectrum.
Nothing depends on R, on the set being run or on the other cells in the run. So the 5 replicates of a cell run with
R = 5 are the first 5 of the same cell run with R = 20, and `summarize()` of those 5 is the stored entry. The data
agree: the 290 stored values of the 58 five-replicate cells equal the first five replicates of the 20-replicate
rerun exactly in nine sets, and to 1.65e-13 in 8D MP034 2017-09-15, whose rerun spectrum was the one-thread one.

**Checks with the fixed program** (an export of 4d6c418, one BLAS thread, one process at a time):

1. **The README commands, for the added cells and one revision cell.** `out/finiteN_parts` held the committed parts
   without the four added cells and without one 5-replicate cell (4D MP032 2017-09-22, nu = 1, ell = 1/2). The
   spectra were the rerun's, bit-identical to the committed ones for these sets. `python3 code/matern_finiteN.py 20
   --first` (583 s) computed exactly the four cells, with 20 replicates. `python3 code/matern_finiteN.py 5` (32 s)
   computed exactly the one cell, with 5 replicates. All five entries equal the stored ones in every field, and the
   combined `out/matern_finiteN.json` equals the committed file as data (every key and value).
2. **Both stages from empty parts for one set.** 8D MP034 2017-09-15, on its spectrum from the two-thread run
   (bit-identical to the committed one): `matern_finiteN.py 20 8704 8D_MP034_0915 --first` (441 s, 3 cells) and
   `matern_finiteN.py 5 8704 8D_MP034_0915` (183 s, 6 cells). All nine cells equal the stored entries in every field.
3. **The whole file.** The procedure's output was assembled from the 20-replicate rerun of every cell, using the
   program's own `keys_for`, `first_run` and `summarize` read from the committed source. Each `first_run` cell kept
   20 replicates and each other cell the first 5, which by the paragraph above is what the two stages compute. The
   four added cells came from the scratch copy with the same list (436 s); its 80 values equal those of check 1.
   8D MP034 2017-09-15 came from check 2. The result: 112 cells, the same 54 with 20 and 58 with 5 replicates as
   stored, and 1,370 replicate values, all equal to the stored file in every field; the file equals the committed one
   as data. With 8D MP034 2017-09-15 taken from the one-thread-spectrum rerun instead, 103 cells are exact and that
   set's 9 cells differ by at most 1.65e-13.

The files are equal as data, not byte for byte. The first computation's cells were written by an earlier `summarize()`
without the `R` field; the combined file appends `R` to those cells, and a cell computed again goes to the end of its
part. No value differs.
